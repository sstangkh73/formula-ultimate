## ลำดับงานและการตรวจสอบ

1. อ่าน source, tests, contracts, ผลงานล่าสุด และ artifacts ที่มี แยกการตรวจโค้ด การเทียบแบบจำลอง และ physical validation
2. ค้นและอ่านแหล่งวิชาการต้นทาง/แหล่งอุตสาหกรรมทางการ บันทึกชื่อ ปี URL ตรง ความเกี่ยวข้อง ข้อจำกัด และระดับการเข้าถึง ตัดรายการซ้ำและแยก paper จากข้อมูลอุตสาหกรรม
3. จัดทำตารางช่องว่าง ลำดับ paper ที่ควรอ่าน และข้อเสนอพัฒนาที่หักล้างได้ โดยไม่บังคับสถาปัตยกรรมรถแบบดั้งเดิม
4. รัน `python -m unittest discover -s tests -q` ตรวจ baseline ปัจจุบัน ถือเป็นหลักฐานซอฟต์แวร์ ไม่ใช่ physical validation บันทึก skips/failures
5. ใช้คำสั่ง Python ตรวจเฉพาะคู่ Markdown ใหม่ รหัสแหล่งข้อมูล URL พาธหลักฐานใน repo และความตรงกันของตัวเลข รัน `git diff --check` และ `git diff --cached --check` ก่อน commit เฉพาะขอบเขต

## เกณฑ์สำเร็จและล้มเหลว

สำเร็จเมื่อมี catalog แหล่งต้นทางที่กว้างและไม่ซ้ำ ประเมินช่องว่างจากโค้ดปัจจุบัน เปรียบเทียบ F1 อย่างตรงไปตรงมา ส่งมอบสองภาษาเทียบเท่ากัน ผ่าน validation และ commit สำเร็จ ไม่แต่งค่าความแม่นยำ F1 ระยะเวลาไล่ทัน หรืออ้างการค้นพบเกินหลักฐาน ความครอบคลุมจำกัดด้วยข้อมูลสาธารณะที่ค้นคืนได้ และต้องระบุรายการที่ยังไม่ได้อ่านฉบับเต็ม

ล้มเหลวเมื่อ citation ไม่มีหลักฐาน ใช้สถานะโค้ดเก่า ขาดคู่ภาษา หรือ validation ที่ล้มเหลวยังไม่ได้แก้ ต้องคง In progress หรือ Stopped หากมีอุปสรรคที่ทำให้จบไม่ได้

## ความเสี่ยงและการควบคุม

รายละเอียดโมเดลและข้อมูล calibration ของ F1 เป็นกรรมสิทธิ์ ใช้หลักฐานความสามารถที่เปิดเผยและระบุความไม่แน่นอน บทคัดย่อไม่พิสูจน์รายละเอียด implementation unit tests ไม่ยืนยันรถจริง หลักฐาน artifact เดิมต้องระบุว่าเป็นหลักฐานเก็บไว้ ไม่ใช่รันใหม่ การค้นกว้างครั้งนี้ไม่อ้างว่าเป็น systematic review

## สิ่งที่ไม่ทำ

ไม่แก้ physics/code/configuration ไม่ทำ experiment ใหม่ ไม่ติดตั้ง solver ไม่ใช้จ่าย ไม่เผยแพร่ภายนอกหรือ push และไม่อ้างว่าผ่านข้อบังคับ F1 งานนี้เสนอการทดลองในอนาคตแต่ไม่รันการทดลองเหล่านั้น
